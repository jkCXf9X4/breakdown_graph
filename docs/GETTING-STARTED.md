# Getting started

This guide goes from the default example to a browsable, editable store with a
ring-folder work area, typed links, and a second solution in a git worktree.
`bdg` has one topology: markdown nodes joined by typed link tokens in their
bodies. A token is `(TITLE)[[REF,TYPE]]`, with the cached title as a prefix;
authors write the bare `[[REF,TYPE]]` and the tool fills the title. The canonical
form has no space after the comma; a legacy single-space `[[REF, TYPE]]` is still
accepted. In-edges are
derived by reversing authored tokens; a back-reference is an authored token in
the other node, not a derived opposite. A view is the weakly connected component
of its anchor, ordered by undirected BFS distance.

You need Python 3.10+ and PyYAML. From a clone, install the package:

```sh
pip install .
bdg --help
```

## 1. See the default store

The repository ships `examples/` as the default store (`ROOT` `1-1`). Linked
nodes carry typed tokens in their bodies, and the store is one component.

```sh
export BDG_ROOT=examples
bdg check
```

```
12 nodes, 0 errors, 0 warnings (view 1-1)
```

The store layout:

```
examples/bdg_graph/nodes/1-1.md
examples/bdg_graph/ROOT          # 1-1
examples/bdg_graph/nodes/4-1.md
```

A node file looks like this:

```markdown
---
id: 1
title: <the intent of this graph>
---
# <the intent of this graph>

The intent breaks down into (Structural claims)[[2-1,breaks_down]] and
(Verification claims)[[3-1,breaks_down]].
```

The filename is identity and version: logical id `1`, version `1`. The rest of
the front matter is arbitrary. A token declares one typed edge to a full
`id-version` ref. The cached title is a prefix generated by the tool from the
target's live title; authors write only the bare token and never edit the
cache by hand. `bdg check` verifies it (`link-title-stale`,
`inline-title-missing`) and `bdg retitle` regenerates it. Tooling appends the
same token as a `- (TITLE)[[REF,TYPE]]` line under `## Links`. Front-matter
`links` is retired (`links-removed`). There is no placement field: membership
and order come from the graph.

There is no second topology and no `contains` key. A node that still declares
`contains` fails `bdg check` with `contains-removed`; `bdg migrate` converts it
(§10).

## 2. Browse the graph

```sh
bdg graph 1-1
bdg graph --depth 1
bdg graph 1-1 --rings 2:3
bdg show 2-1+1 --max-chars 400
bdg find closure --limit 3
bdg path 4-1
bdg out 1-1
bdg in 4-1
bdg views
```

- `graph` renders ring sections from an anchor, with authored `→ out` edges and
  derived `← in` edges. The anchor is ring 0; ring 1 is split into `children`
  and `parents`; deeper rings are numbered. `bdg graph` is the only view
  renderer.
- `--depth N` stops traversal after `N` hops. `--rings A:B` keeps an
  inclusive ring range in the output but keeps traversing through hidden nodes;
  the anchor is always included.
- `show REF+N` prints the node body plus rings `0..N`, each node once. Arrival
  arrows label the direction (`→` child, `←` parent).
- `find` searches titles, summaries, bodies, and front-matter fields.
- `path` prints the shortest undirected chain from the anchor, with an arrow on
  every step. `4-1` has two parents; the path is deterministic but is only one
  of several equally short routes.
- `out` lists authored out-edge tokens; `in` lists derived reverse edges.
- `views` lists one representative per component, marking the default with `*`
  and the work-area anchor.

A node reached through several neighbours appears once in a view. Multiple
parents, cycles, and back-edges are legal.

Exit codes: `bdg check` returns 1 on errors and 0 on clean. Structural commands
return 2 on refusal.

## 3. Check the graph

```sh
bdg check
```

```
0 errors, 0 warnings
```

The graph checks make the undirected view meaningful:

- tokens resolve to existing full refs and are kept in ascending target order;
- a token that does not match `[[REF,TYPE]]` is `inline-malformed`, and the
  same type and target twice on one node warns `inline-duplicate`;
- a bare token warns `inline-title-missing`, and a cached `(TITLE)` that
  differs from the target's live title warns `link-title-stale`; run
  `bdg retitle` to fill or refresh either, and rendering still uses the live
  title;
- a bare `ROOT` ref is `bare-ref`, and malformed `ROOT` content is
  `invalid-root`;
- a node outside the default component warns (`graph-orphan`); out-degree above
  200 warns (`graph-wide-fanout`);
- a reachable duplicate version warns (`graph-duplicate-version`);
- a node declaring `contains` is `contains-removed`, and one declaring
  front-matter `links` is `links-removed`.

Cycles, back-edges, reciprocal edges, and direction are not errors. Only a
self-loop on one ref is refused by `bdg link`.

Structure is edited with links:

```sh
bdg new --parent 1-1 --type breaks_down --field title="A new claim"
bdg link 2-1 8-1 --type supports
bdg link 8-1 2-1 --type supported_by
bdg unlink 2-1 8-1 --type supports
```

`bdg new` allocates the next global id at version 1 and appends a typed token to
the parent's `## Links` section; `--type` defaults to `breaks_down`. It has no
placement flags. Without `--parent`, the node starts its own component.
`bdg link` appends `- (TITLE)[[TO,TYPE]]` to the source in call order, writing
the target's live title; existing lines are untouched, so add targets in
ascending order or re-sort the section. Back-edges and cycles are legal. A
back-reference is a second authored token on the other node with its own type —
there is no `--symmetric`. `bdg retitle` regenerates cached titles from the live
titles when a target's title changes.

## 4. Edit in the work area

`bdg work` renders a view as ring folders of symlinks in the project's single
writable work area, `<project>/bdg_work/`. Editing a link edits the store.

```sh
bdg work 1-1
bdg current                 # <project>/bdg_work (view 1-1)
work_dir=$(bdg current --path)
ls -R "$work_dir"
```

```
0/1-1_Verify the undirected graph.md          0/INDEX.md
1/2-1_Structural claims.md
1/3-1_Verification claims.md                  1/INDEX.md
2/4-1_Two parents, one node.md
2/5-1_The component view.md                   2/INDEX.md
   ... one symlink per node, rings 3-4 ...    3/INDEX.md  4/INDEX.md
INDEX.md    REFS.md     AGENTS.md
```

Every node `.md` is a symlink at `{distance}/{ref}_{title}.md`, so ring 0 is
`0/1-1_Verify the undirected graph.md`, ring 1 is
`1/2-1_Structural claims.md`, and ring 2 is
`2/4-1_Two parents, one node.md`. Titles are literal (spaces kept), and
`{title}` falls back to the ref when a node has no `title` front matter (an
untitled `2-1` is `2-1_2-1.md`). The layout is recorded in
`REFS.md` as `# Layout — <template>`
(`# Layout — {distance}/{ref}_{title}.md` for the
default), so a later plain `bdg work REF` reuses it. `--path-template` overrides
the ring folders and `--flat` restores one symlink per node at its store basename
(recorded as `# Layout — flat`, sticking on later rebuilds; `--flat` with
`--path-template` is an error). Every folder that directly holds node files gets
its own `INDEX.md` with folder-relative links (so each ring folder has one), and
empty folders are not preserved. `INDEX.md`, `REFS.md`, and `AGENTS.md` are
regular generated files.

The root `INDEX.md` has ring sections:

```markdown
## Active

- [<title>](0/1-1_Verify the undirected graph.md) — [real file](../bdg_graph/nodes/1-1.md)

## Distance 1 — children

- [<title>](1/2-1_Structural claims.md) — [real file](../bdg_graph/nodes/2-1.md)

## Distance 2

- [<title>](2/4-1_Two parents, one node.md) — [real file](../bdg_graph/nodes/4-1.md)
```

`REFS.md` is the sorted navigation table:

```markdown
# References — view 1-1
# Layout — {distance}/{ref}_{title}.md

| Path | Ref | Kind | Distance | Title |
| --- | --- | --- | --- | --- |
| `0/1-1_Verify the undirected graph.md` | 1-1 | active | 0 | <title> |
| `1/2-1_Structural claims.md` | 2-1 | child | 1 | <title> |
| `2/4-1_Two parents, one node.md` | 4-1 | - | 2 | <title> |
```

The `# References — view REF[+N]` header is the active node of the area.
`bdg current`, `bdg edit`, `bdg current --status`, and `bdg work --repair` read it.
There is no separate state file.

`bdg edit REF` prints the ref's absolute path inside the active view and errors
if the ref is not there. `bdg current` is read-only; `--path` prints only the
path and `--view` only the ref, and it errors if no area exists.

`bdg current --status` reports `ok`, `missing`, `wrong-target`, `detached`,
`stray`, or `stale-ref`. If an editor replaces a symlink with a regular file:

```sh
bdg current --status
bdg work --repair
```

`bdg work --repair` writes the detached content to the original node, refuses
files without valid front matter, and re-links them.

There is exactly one writable work area. `bdg work REF` switches it to another
view by replacing its contents: stale links are removed, and `INDEX.md`,
`REFS.md`, and `AGENTS.md` are rewritten. Never keep two work folders side by
side.

A work area may also materialize only rings `0..N` of a component:
`bdg work REF+N`, or `bdg work REF --depth N`, where `0` materializes the anchor
alone and `--depth` overrides a suffix. The view itself is still the whole
component. The generated headers carry `REF+N`, so `bdg current --view` reports
it and `bdg edit` only resolves refs that are materialized. A rebuild with a
different depth, or a plain `bdg work REF`, replaces the area.

```sh
bdg work 1-1+1      # rings 0 and 1
bdg current --view  # 1-1+1
bdg work 1-1        # restore the full component
```

Read-only projections (`bdg pack`, `bdg graph --format dot|svg`) are separate
disposable outputs, not a second work area. They render the same view but their
default layouts differ: `bdg work` writes ring folders, while `bdg pack` writes
flat regular files plus a ring-section `INDEX.md` and nests only with
`--path-template`. `bdg graph --format` writes a string render.

## 5. Create a store

```sh
mkdir -p ~/stores/my-graph
cd ~/stores/my-graph
bdg init
```

```
bdg_graph/nodes/1-1.md
.gitignore          # bdg_work/
```

```markdown
---
id: 1
title: Root
---
# Root
```

`bdg init` always writes a graph root with no links and no placement key; there
is no `--graph` flag because graph is the only topology. Add nodes and check:

```sh
bdg new --parent 1-1 --type breaks_down --field title="Why does this exist?"
bdg new --parent 1-1 --type breaks_down --field title="What is true?"
bdg check
```

```
3 nodes, 0 errors, 0 warnings (view 1-1)
```

`bdg graph 1-1` renders rings `0` and `1`. `bdg new` appends a typed token to the
parent's `## Links` section; it writes no position.

By default the work area groups nodes into ring folders named
`{distance}/{ref}_{title}.md`; `--flat` uses each node's store basename instead.
A `--path-template` may group by an existing field such as `{distance}` or
`{group}`; the template adds no placement key. `group`, `section`, `folder`, and
`home` are inert front matter: they place nothing unless a template names them.

To change the view, edit the links. There is no separate move command: position
is derived from edges and undirected distance.

## 6. Typed links and freshness

The body carries typed tokens. Add a propagating edge and track freshness:

```sh
bdg link 2-1 3-1 --type supports --propagates
bdg stale
```

Then edit a target through its work area, or open it with `bdg edit REF`. A
propagating edge records `pinned` under the target's ref in the source node's
top-level `freshness:` map; `bdg stale` reports when the target moves.
`--propagates` is opt-in; a `see_also` edge never goes stale. The pinned hash
ignores token lines and the `## Links` heading, so adding an edge does not
invalidate another edge's pin.

Repin after reviewing the change:

```sh
bdg stale --fix REF         # or --all
bdg stale
```

Cached link titles are tool-maintained in the same spirit: after a target is
retitled, run `bdg retitle` to regenerate every cache in the store (or narrow
with `REF`); `bdg retitle --dry-run` reports what would change.

Remove an edge:

```sh
bdg unlink FROM TO --type supports
```

Pins are body hashes, so they survive a rebase.

## 7. Versions and switching

Two separate moves: change the default anchor, or switch the view held by the
work area.

```sh
bdg root 1-1                 # write ROOT; commands default here
bdg root                     # 1-1  (ROOT)
bdg work 1-1                 # switch the work area
bdg current                  # <project>/bdg_work (view 1-1)
bdg root --clear             # back to the lowest component member
```

`ROOT` is one full ref on one line at the store top level. An explicit ref where
a command takes one still wins over it; with no `ROOT`, the store uses the
lowest member of its first component. `bdg check --view REF` only narrows
reporting, not the checked anchor. `bdg root` changes the default anchor used by
commands but does not rewrite the view already in `<project>/bdg_work/`; run
`bdg work REF` for that. `bdg views` lists component representatives and marks the
default with `*`.

Versions are node-local alternatives inside one branch:

```sh
bdg versions 1
bdg clone 1-1 --version 2
bdg replace 1-1 1-2
```

`bdg clone REF` copies a ref to the next free version of the same logical id (or
to `--version N`) and keeps the source file's link tokens; it wires nothing into
a view. `bdg clone REF --subtree` clones the whole weakly connected component and
rewrites the cloned token refs whose target was also cloned; a depth prefix
keeps edges that leave the prefix pointing at the originals. `--depth N`
narrows the clone to rings `0..N` and implies `--subtree`.
`--version` cannot be combined with `--subtree` or `--depth`.
`bdg replace OLD NEW` is the separate wiring step: it repoints every inbound
link and sets the rewritten tokens' cached title to NEW's live title, or
repoints `ROOT` when OLD is the store root; OLD's file stays as a peer.

An edge pins a full ref, several parents are allowed, and a view warns
(`graph-duplicate-version`) when two versions of one id are reachable. Repoint
the edge whose peer you want to change.

## 8. A second solution with git

A solution is a git branch in a worktree; the flat store is the merge unit.

```sh
git init -b main
git add -A
git commit -m "init store"

bdg solution new sol-a
```

`bdg solution new` prints:

```
worktree /home/you/stores/sol-a
branch sol-a
project .
cd /home/you/stores/sol-a
bdg work 1-1
```

The project directory is printed relative to the worktree. In a nested project,
`cd` into the printed project path instead, for example
`cd /home/you/stores/sol-a/examples`, then run the printed `bdg work` command.

```sh
cd ../sol-a
bdg work 1-1
$EDITOR "$(bdg edit 1-1)"
bdg check
git add -A && git commit -m "sol-a: alternative intent"
```

Compare without switching:

```sh
cd ../my-graph
git diff main..sol-a -- bdg_graph/nodes/
bdg solution list
```

Remove the checkout when done; the branch remains:

```sh
bdg solution remove sol-a
```

If the project is nested inside the repo, use the printed `cd` line to enter the
project path inside the worktree, for example `cd /home/you/stores/sol-a/examples`.
Store discovery then finds `bdg_graph/` there. From the worktree root it also
finds a single store below the current directory; `BDG_ROOT` is only needed when
several stores are below that root.

## 9. Feed an agent

Two modes:

```sh
# writable: the single work area for one view
bdg work 1-1
bdg current

# read-only snapshot: fresh nodes, plus STALE.md and AGENTS.md
bdg pack 1-1 --fresh --out /tmp/bdg-context-1-1
```

`bdg work` writes `<project>/bdg_work/` and is the only work area; the pack
directory is a disposable copy, not a second area. Both contain an
`AGENTS.md`; the work area also records the branch, commit, and worktree, and
its `REFS.md` names the active view. Tell the agent to read exactly one
directory and not to read outside it, and to use `bdg edit REF` rather than
guessing paths. To change view, switch the same area with `bdg work REF` and
confirm with `bdg current`.

## 10. Use an existing markdown tree

There is no generic importer yet. The pattern is:

1. One file per node version under the store's `nodes/` (`bdg_graph/nodes/` in a
   project layout), named `<id>-<version>.md` with a running integer id and a
   version starting at `1`.
2. `id` matches the logical id in the filename.
3. Link tokens name typed edges with full refs, in ascending target order. No
   placement key is needed: the view is the component of the anchor and the
   order is BFS distance. If the tree must read as a hierarchy, encode the
   parent -> child tokens; a `child` label comes from the authored direction.
4. Prose citations are separate; an edge is a link, not a bibliography entry.
5. The work area groups nodes into ring folders by default
   (`{distance}/{ref}_{title}.md`); `--path-template` overrides naming and
   `--flat` restores store basenames.

An older store that used `contains` or authored placement is converted in place:

```sh
bdg migrate --dry-run     # print the plan
bdg migrate               # contains/links -> body tokens; retired keys stripped
bdg retitle               # refresh cached titles from live titles
bdg check                 # clean
```

`bdg migrate` writes converted edges as sorted body tokens, converts legacy
suffix tokens `[[TYPE,REF]](TITLE)` or `[[REF,TYPE]](TITLE)` to the prefix
form `(TITLE)[[REF,TYPE]]`; it normalizes either component order to ref-first,
fills missing titles, uses `--type` (default `breaks_down`) for `contains` edges,
moves per-link freshness into the `freshness:` map, removes the retired
placement fields, and keeps `section` as inert front matter. It is idempotent
and leaves a token-only store untouched. `bdg retitle` is the explicit refresh
step: it regenerates every cached title in the store or a view from each
target's live title and leaves unresolved targets untouched.

`examples/` is the default worked project: a twelve-node graph under
`examples/bdg_graph/` with one file per node version, typed tokens in the linked
bodies, one component, rings 0 through 4 from `1-1`, and no `contains`.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `bdg: unknown ref '1-1'` | No store found, or the ref is absent from the selected view. Run from the project root or store root, or set `BDG_ROOT` to the directory containing `nodes/` (or `bdg_graph/nodes/`). |
| `bdg check` sees the wrong store | `BDG_ROOT` or `--root` points elsewhere. `bdg` uses the nearest `nodes/` or `bdg_graph/nodes/` upward. |
| `root-ref-missing` / `invalid-root` | The `ROOT` file names an absent ref or is malformed. Fix it, or run `bdg root --clear`. |
| `contains-removed` / `links-removed` | The store still declares `contains` or front-matter `links`. Run `bdg migrate --dry-run`, then `bdg migrate`. |
| `inline-malformed` | A `[[...]]` fragment is not `[[REF,TYPE]]` with a full ref. Fix the token; escape it as `\[[` to show it literally. |
| `inline-duplicate` | One node declares the same type and target twice. Remove one with `bdg unlink`. |
| `inline-title-missing` | A token is bare. Run `bdg retitle` to fill the cached title; do not hand-write it. |
| `link-title-stale` | A cached `(TITLE)` differs from the target's live title. Run `bdg retitle`; rendering already uses the live title. |
| `invalid-freshness` | `freshness:` must key full target refs to a mapping with string `pinned` and boolean `propagates`. |
| `bare-ref` / `invalid-ref` in data | `ROOT` needs a full `id-version` ref; a bare ref inside a token is `inline-malformed`. Convert a classic bare-file store once with `bdg migrate`. |
| A cycle or back-edge is reported | It should not be. Update to the current version; only a self-loop is refused by `bdg link`. |
| `graph-orphan` | A node is outside the default component. Link it in, or anchor on its component with `bdg graph REF` / `bdg work REF`. |
| `bdg work` refuses to switch | `bdg_work/` has detached or stray files. Run `bdg current --status`, then `bdg work --repair` to keep them or `--clean` to discard them. |
| `bdg current` errors | No work area exists. Build one with `bdg work [REF]`. |
| `bdg edit REF` errors | The ref is not in the active view. Switch with `bdg work REF` or use a ref that is present. |
| Edit did not reach the node | The editor replaced the symlink. Run `bdg current --status`, then `bdg work --repair`. |
| Want two work folders | Not supported. `bdg_work/` is the single area; switch with `bdg work REF`. |
| `bdg_work/` appears in git status | `bdg init` adds it to `.gitignore`; add `bdg_work/` if the project predates that. |
| Work folder points at missing files | The branch changed under the layout. Rebuild with `bdg work REF --clean`. |
| Size warning on a node | Cosmetic by default. Split the node, or pass `--max-lines` / `--max-chars`. |
