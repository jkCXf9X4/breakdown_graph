# Operation — how bd_tree is run

## Purpose

The operator deciding how to install, locate, scaffold, convert, and safely switch a bd_tree project uses this layer as the runbook of record; without it, a routine upgrade or view switch silently leaves the store converted incorrectly or edits unmerged.

---

Routine operation owns the six moves that keep a store usable across tool changes and concurrent sessions; the store model and each command's own semantics belong to the layers those moves exercise.

- State: all six contracts are current; none is open work. The operator owns preservation across install and upgrade, the one explicit conversion, repair before a view switch, store discovery, project scaffolding, and write serialization. Derived from the six member bodies, not copied from any one.
- Exception: none of the six runs implicitly. An upgrade does not migrate, discovery does not write, and `bd init` refuses a non-empty store rather than merging into it.
- Failure: the layer fails when an operator assumes the tool repairs or converts on its own, leaving a retired store unconverted or detached edits unrepaired.

Members, in id order:

1. (Install and upgrade preserve the store)[[36-1, breaks_down]] is the first move, because every later operation runs against an installed tool.
2. (Migration converts retired data)[[37-1, breaks_down]] is the one explicit conversion, so an upgrade never rewrites the store on its own.
3. (Detached edits block a switch until repair)[[38-1, breaks_down]] protects unmerged edits when the work area is replaced.
4. (Discovery walks up, then scans down)[[39-1, breaks_down]] locates the store before any command touches it.
5. (Init scaffolds a hidden-store project)[[40-1, breaks_down]] creates the project layout that the other moves operate on.
6. (Writers serialize on an advisory lock)[[41-1, breaks_down]] keeps concurrent sessions from interleaving writes.
