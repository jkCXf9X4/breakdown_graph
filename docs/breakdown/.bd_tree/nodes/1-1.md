# Product Breakdown — bd_tree

## Purpose

The engineer or agent deciding where a bd_tree fact belongs uses this node as
the entry map; without it, an implementation detail is argued as intent and the
layer tree cannot be navigated.

---

bd_tree is a local, git-native graph of markdown nodes. This breakdown follows
the product from intent through operation, then the open work and the review;
history is separate.

Layers, in reading order:

1. (Intent — why bd_tree exists)[[2-1, breaks_down]] names the failure the tool must correct, so it is the first rung.
2. (Product — what bd_tree promises)[[3-1, breaks_down]] states the commitments that follow from that intent.
3. (Architecture — how bd_tree is organized)[[4-1, breaks_down]] fixes the invariants those commitments rest on.
4. (Implementation — where bd_tree is built)[[5-1, breaks_down]] shows which module owns each invariant.
5. (Verification — how bd_tree proves its claims)[[6-1, breaks_down]] states the gate that accepts the implementation.
6. (Operation — how bd_tree is run)[[7-1, breaks_down]] covers install, discovery, migration, and repair.
7. (Evolution — what might change)[[8-1, breaks_down]] holds the candidates that are not yet selected.
8. (Review — what is still contested)[[9-1, breaks_down]] states what the check cannot certify.

The entry map records (Decisions — why bd_tree changed)[[10-1, records]] as
history, outside the state layers. A fact that answers two layers is split; a
fact that answers none is outside this breakdown.
