# Writers serialize on an advisory lock

## Purpose

The operator running two `bdg` writes against one store uses this claim to know the second waits rather than interleave; without it, concurrent structural edits can lose a token or publish a partial node.

---

Every structural writer runs under one exclusive inter-process lock keyed by the store's real path; the lock file lives in the system temp directory, not in the store or git, and the kernel releases it if a holder dies (`src/bdg/fsutil.py:34-87`). The lock operates inside (Ops performs body-preserving structural edits)[[29-1,operates]]: `_serialized` wraps each writer, and `bdg work` takes the same lock before it rebuilds the area (`src/bdg/ops.py:148-157`, `src/bdg/work.py:644`). Node files are published with a temp file plus rename, so readers see the old file or the new one, never a truncated document (`src/bdg/fsutil.py:106-138`). The failure is a write made outside `bdg`: it takes no lock, so two such writers race.
