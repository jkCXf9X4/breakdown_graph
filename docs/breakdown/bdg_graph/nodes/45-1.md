# Three-way merge between versions

## Purpose

The engineer deciding how two node versions reconcile uses this work item to
bound a merge path; without it, manual synthesis is mistaken for a merge and
conflicting edits are resolved by hand.

---

Question: should the tool compute a three-way merge between node versions, or
keep reconciliation as manual synthesis followed by git? The design and README
both record that no three-way merge exists and that synthesis is manual, while
branches and versions stay disjoint (`docs/DESIGN.md:627-628`, `README.md:425`,
`docs/BRANCHES-AND-VERSIONS.md:1-17`).

- Done when: base, left, and right inputs yield a merged version plus a conflict
  report, the merged file passes `bdg check`, and inbound tokens are repointed
  only after the merge is accepted; a manual-only outcome is recorded as a
  rejected alternative, not left implicit.
- Changes: (A filename encodes identity and version)[[18-1,changes]] would be
  revised if the tool starts producing a merged version.
- Status: suggested; no merge path is built, and versions still reconcile by
  manual synthesis (`docs/DESIGN.md:628`).
