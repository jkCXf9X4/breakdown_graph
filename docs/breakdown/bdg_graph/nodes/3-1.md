# Product — what bdg promises

## Purpose

The engineer or agent deciding whether a behaviour is a promise uses this group
as the product rung; without it, an internal layout choice is defended as a
commitment to integrators.

---

Product is the boundary bdg promises an integrator or an agent, not how the
tool achieves it. Four promises hold at that boundary, in the order below:

1. (Front matter stays project-defined)[[14-1, breaks_down]] keeps the project's vocabulary out of the tool's schema.
2. (Git owns the solution boundary)[[15-1, breaks_down]] makes one branch or worktree the unit that isolates a solution.
3. (One project has one writable work area)[[16-1, breaks_down]] fixes the single place where edits are written.
4. (One store yields many read-only projections)[[17-1, breaks_down]] makes every other surface derived and disposable.

The four share one split: bdg owns identity, links, and derived views, and
refuses to own the project's vocabulary, its branch policy, or a second writable
copy. Membership and order are the four authored tokens above; the shared
condition is derived from their bodies, not copied from any one.

- State: all four are boundary promises an integrator can observe; none depends
  on a file name, a branch, or a projection layout.
- Exception: the tool writes the one-line `ROOT` default-anchor file inside the
  store, while a working folder may carry its own one-line `.bdg_root` pointer
  naming that store (`README.md:194-220`, `docs/DESIGN.md:84-85`).
- Failure: the group is stale when a member's surface gains a second writable
  copy or a hand-maintained projection, or when a promise is restated as an
  implementation choice such as a path template.
