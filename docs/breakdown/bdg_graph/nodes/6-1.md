# Verification — how bdg proves its claims

## Purpose

The reviewer deciding whether a bdg claim is proven uses this layer to see
which evidence exists and what remains unverified; without it, a green check is
read as proof of every claim.

---

Verification rests on five executable claims, all repo-local; each item states
the evidence it supplies. Their shared condition is that each can be
re-run from a checkout; none certifies prose, purpose presence, token placement,
or chain credibility, and the example proves shape rather than scale. The layer
fails if a claim depends on a test that does not run, a store that has drifted, or
a warning read as acceptance; no CI configuration exists yet
(`docs/DESIGN.md:642-643`).

Members, in reading order:

1. (Check validates store and view invariants)[[31-1, breaks_down]] is first
   because the other four are read against its verdict.
2. (The example store is the clean reference)[[32-1, breaks_down]] is the fixed
   reference the remaining evidence is compared against.
3. (Temporary stores drive the test suite)[[33-1, breaks_down]] is the test
   substrate the two evidence-bound claims rely on.
4. (Stale checking is view-scoped)[[34-1, breaks_down]] is the freshness bound,
   narrower than the whole-store gate.
5. (Exit codes separate success, navigation, and structure)[[35-1, breaks_down]]
   closes the order because it reports the gate's result to a caller.
