# Model and checker separate shape from validation

## Purpose

The developer adding a validation rule uses this node to decide whether it
belongs in parsing or in the checker; without it, a bad file makes the whole
store unreadable instead of reportable.

---

`model` defines the parsed shape and the derived queries; `checker` only judges
them. `Node`, `Link`, `Store`, and `View` are dataclasses over already-loaded
data, with `Store.neighbors` and `View.distance` deriving relationships without
writing (`src/bdg/model.py:38-105`, `179-260`, `338-361`). `checker.check`
loads the store, collects `Issue(level, code, message)` records from the store
scan, the graph audit, freshness, titles, and size, and returns a `CheckResult`;
it raises only when loading itself fails (`src/bdg/checker.py:169-261`). The
parsed `Link` and the token checks implement
(Typed links define the component view)[[19-1, implements]] by treating a token
as data, never as prose. The invariant is severity as data: a malformed file
stays loadable and reportable. Failure is validation inside the loader, which
makes one bad file hide every good node.
