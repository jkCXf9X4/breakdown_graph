# Data-driven paper table

`thesis/build.py` encodes each included paper as literal entries in two lists.
`ensure_included_paper_pdfs` lists a PDF path and a build script per paper.
`stage_included_paper_pdfs` lists a citekey and a source PDF per paper.
Paper 1 appears only as a comment in the first list and as a path in the second.
Paper IV is labelled Paper 6 in `build.py` and gets its own code path in both functions, with a soft-fail.
**Evidence:**

Adding a paper means editing two lists and any extra branch.
The lists can disagree about a paper, and nothing checks that they do.
Paper IV's soft-fail is a special case that a column could carry.
A reader learns the rules by reading code instead of data.

`thesis/build.py:27-33` holds the build targets for Papers 2-5.
`thesis/build.py:63-73` holds the staging mappings for Papers 1-5.
`thesis/build.py:43-52` and `thesis/build.py:79-85` carry the Paper IV branch and its skip message.
`thesis/build.py:75-76` raises on a missing staged PDF; the Paper IV path never raises.
`thesis/build.py:117-118` calls the two functions in sequence.
The last green build produced 154 pages.
**Acceptance:**

- One table holds paper, build command, PDF path, and soft-fail flag.
- Both functions read that table, and no paper appears twice.
- Adding a paper touches exactly one table entry.
- The build still produces 154 pages after the refactor.
- Paper IV keeps its soft-fail, expressed as a column value.
**Out of scope:**

- Whether Paper IV should soft-fail at all (`7`).
- Pin and metadata for Paper IV (`19`).
- Build gate acceptance and its page count (`51`).
- Whether a paper should be typeset instead of staged (`21`).

- Pin mechanics and submodule updates (`25`).
- Appendix include guards (`7`).
- Build gate acceptance (`51`).
