# Repoint archived decision states at the current leaves

`traceability-map.md` is generated from each archived record's `state:` field, so a stale path in a record becomes a stale pointer in the map.
The 2026-11-02 product restructure moved the examined-object leaf into a folder and split the kappa-requirements leaf into four requirement leaves.
The archived records whose `state:` still names the old examined-object path remain stale.
The record whose `state:` names an intent path that no longer exists remains stale too.
**Evidence:**

The map is the only generated surface that ties a leaf to its decisions, and it currently points at a file that does not exist.
A reader who follows it lands nowhere, and the gap is invisible to `pb check --strict` because the tool validates artifacts but not state paths.

- `docs/breakdown/traceability-map.md` lists a state path under `intent/` that no file occupies after the restructure.
- The same map lists an intent state path with no matching leaf.
- Removal of the superseded `INFO-*`/`REQ-*` stubs left two more stale pointers: the drop-running-example record's `state:` names the deleted `manuscript/kappa-structure.md`, and the in-repo-case record's `artifacts:` name the deleted `manuscript/kappa-structure.md` and `evidence/research-methods.md`.
- `pb archive list` shows the three product records and the intent record as accepted.
**Acceptance:**

- Every `state:` field in every archived record resolves to an existing leaf under `docs/breakdown/`.
- The repointing is done as a new dated record that supersedes the four records, not by editing history in place.
- `pb registers` regenerates the map with no dangling state path, and the result is checked by hand once.
**Out of scope:**

- Rewriting the content of any decision record.
- Moving the leaves back to their former paths.

- The leaf contents those records name (`6`, `29`–`42`).
- How records are validated (`pb archive`).
